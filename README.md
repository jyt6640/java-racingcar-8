## 📋 기본 기능 목록

- [X] 주어진 횟수 동안 n대의 자동차는 전진 또는 멈출 수 있다.
- [X] 각 자동차에 이름을 부여할 수 있다. 전진하는 자동차를 출력할 때 자동차 이름을 같이 출력한다.
- [X] 자동차 이름은 쉼표(,)를 기준으로 구분하며 이름은 5자 이하만 가능하다.
- [X] 사용자는 몇 번의 이동을 할 것인지를 입력할 수 있어야 한다.
- [X] 전진하는 조건은 0에서 9 사이에서 무작위 값을 구한 후 무작위 값이 4 이상일 경우이다.
- [X] 자동차 경주 게임을 완료한 후 누가 우승했는지를 알려준다. 우승자는 한 명 이상일 수 있다.
- [X] 우승자가 여러 명일 경우 쉼표(,)를 이용하여 구분한다.
- [X] 사용자가 잘못된 값을 입력할 경우 IllegalArgumentException을 발생시킨 후 애플리케이션은 종료되어야 한다.
- [X] 기본 기능 구현 완료

### 입출력 요구 사항
#### 입력
- 경주할 자동차 이름(이름은 쉼표(,) 기준으로 구분)
```
pobi,woni,jun
```
- 시도할 횟수
```
5
```
#### 출력
- 차수별 실행 결과
```
pobi : --
woni : ----
jun : ---
```
- 단독 우승자 안내 문구
```
최종 우승자 : pobi
```
- 공동 우승자 안내 문구
```
최종 우승자 : pobi, jun
```
- **실행 결과 예시**
```
경주할 자동차 이름을 입력하세요.(이름은 쉼표(,) 기준으로 구분)
pobi,woni,jun
시도할 횟수는 몇 회인가요?
5

실행 결과
pobi : -
woni :
jun : -

pobi : --
woni : -
jun : --

pobi : ---
woni : --
jun : ---

pobi : ----
woni : ---
jun : ----

pobi : -----
woni : ----
jun : -----

최종 우승자 : pobi, jun
```

### 1. 랜덤 값 테스트
> 랜덤 값을 테스트할 때 랜덤 함수를 직접 사용하면 테스트 결과를 예측할 수 없어 어려움이 있었습니다.<br>
> 처음에는 전진 여부만 구분하면 되지 않을까 생각해서 단순히 전진만 시키는 기능을 만들었습니다.
>
> 그런데 전진 기능을 만들고 나서 생각해보니, 이전 스터디와 코드 리뷰에서 여러 값을 입력받아 테스트할 수 있는 방법을 본 기억이 났습니다.
> 그래서 `@ValueSource`를 활용하여 다음과 같이 테스트를 분리했습니다:
> - 전진하는 값들만 입력했을 때 → 자동차가 전진하는지 확인
> - 정지하는 값들만 입력했을 때 → 자동차가 멈춰있는지 확인
>
> 이렇게 두 가지 경우로 나누어 테스트하니, 랜덤한 값을 받지 않고 랜덤 값의 범위 내에 있는 값으로만 테스트 하니 제대로 동작하는지 검증할 수 있었습니다.<br>
> 추가적으로 미션이 끝나갔을 때 쯤 다른 방법은 없나 구글링 해봤는데 `Mockito`라는 도구를 잠깐 읽어 보았는데 다음 미션을 할 때 참고해서 작성해 볼 것 같습니다 !

### 2. TDD와 DDD
> 이전 주차에서는 TDD가 어떻게 돌아가는지 파악하고 사용법을 익히는 데 집중했다면,<br>
> 이번 주차에는 작은 기능 하나를 만들 때마다 테스트를 먼저 작성하고, 기능 완성 후 리팩토링하는 흐름으로 진행했습니다.
>
> 작은 단위로 테스트를 먼저 작성하니 구현해야 할 기능이 명확해지고,<br>
> 리팩토링 시에도 기존 기능이 제대로 동작하는지 바로 확인할 수 있어서 좋았습니다.
>
> 도메인 주도 설계에 대해 커뮤니티 글을 읽으면서 고민했습니다.<br>
> 아직 완벽히 이해하지는 못했지만, **"일단 도전하자"** 는 마인드로 다른 코드와 예제를 참고하며 적용해봤습니다.<br>
> 부족한 부분이 많을 것 같아, 많은 지적과 개선 방향을 알려주시면 감사하겠습니다!
> 
> 추가적으로 공부를 따로 한 후에 블로그에 작성도 해보겠습니다 !

### 3. SRP(단일 책임 원칙)
> 우테코 클린코드 체크리스트의 **"메서드가 한 가지 일만 담당하도록 구현했는가?"** 항목에 대해 많이 고민했습니다.<br>
>
> 특히 시도 횟수를 입력받을 때 String을 int로 변환하는 과정에서 고민이 많았습니다.<br>
> int 범위를 초과하면 오류가 발생하는데, 이 검증 로직을 `Validator`에서 처리해야 할지 고민했습니다.<br>
> 현재는 `InputParser`에서 범위 초과 시 에러를 처리하도록 구현했는데, 이 부분에 대한 의견을 듣고 싶습니다!<br>
>
> 다른 로직들도 하나의 메서드가 하나의 역할만 수행하도록 작성하려고 노력했는데,<br>
> 이 부분도 함께 확인 부탁드립니다!

### 4. 개발 순서
> 예상했던 구현 순서와 실제 개발 과정이 달랐습니다.
>
> 솔직히 처음에는 **"일단 돌아가는 코드를 만들자"** 는 생각으로 제가 알고 있던 개념만으로 최소 기능을 완성했습니다.<br>
> 이전 코드 리뷰 내용과는 별개로 일단 동작하는 버전을 만든 후, 리팩토링과 기능 추가를 하면서 점진적으로 개선해 나갔습니다.
>
> 이전 주차에서 검증과 추출을 먼저 진행하며 도메인의 중요성을 깨달았고,<br>
> 이번에는 도메인을 먼저 설계하고 개발을 진행했습니다.
>
> 그 결과, 개발 속도와 로직 구성 측면에서 큰 차이를 느꼈습니다.<br>
> - **문자열 계산기**: 배열로 시작 → 컬렉션으로 전환하는 큰 리팩토링 필요 (시간 소요 ↑)<br>
> - **자동차 경주**: 도메인 우선 설계 → 점진적 확장 (큰 리팩토링 과정 생략, 빠른 개발 + 정확성 ↑)
>
> 아직 한 가지 고민이 남아있습니다.<br>
> 1. 최소한의 개념으로 일단 완성 시킨 후 → 리팩토링<br>
> 2. 테스트 작성 → 기능 개발 → 즉시 리팩토링
>
> 어떤 방식이 더 효과적일지에 대해 계속 고민 중입니다.
